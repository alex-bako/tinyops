# Plan — M1.T2 Invite email on create and Resend

## Objective
Creating a workspace invitation emails the invitee a sign-in link that lands on Join (T1); Resend sends it again; a send failure keeps the invitation and tells the inviter. Existing TinyOps users keep their single account (INV-11).

## Acceptance mapping (docs/roadmap/milestones/M1.md → checks)
- New address → `auth.admin.inviteUserByEmail(email, { redirectTo: <callback>?next=/join })` → `invite-mailer.test.ts`.
- Existing user (profiles row for the address) → `auth.signInWithOtp({ shouldCreateUser: false, emailRedirectTo })`; never a second account → `invite-mailer.test.ts`.
- Send failure → invitation persisted, result carries `warning: "invite_email_failed"`, Members shows "Invite saved, email not sent" → `application.test.ts`, `section-members.test.tsx`.
- Resend on a pending row sends again, button briefly disabled; owners/admins only; revoked/accepted rows are not listed (already filtered) → `application.test.ts`, `section-members.test.tsx`.
- Locally: email visible in the mail viewer (http://127.0.0.1:54324) → manual check recorded in execute evidence.

## Design (ponytail)
- Port: `apps/web/features/workspaces/invite-mailer.ts` — `WorkspaceInviteMailer { sendInvite({ email }) }` + `createSupabaseInviteMailer({ admin, getOrigin })`. Existing-user branch decided by `profiles.email` via the admin client; `inviteUserByEmail` "already registered" also falls back to the magic link.
- Application: optional `mailer`; `inviteMember` sends after the store insert; new `resendInvitation(invitationId)` (permission = `canManageMembers`). `WorkspaceActionResult.data` gains optional `warning`.
- Actions: `resendWorkspaceInviteAction`; request origin helper shared with login (`lib/auth/request-origin.ts`).
- UI: context exposes `notice` + `resendInvitation`; Members section enables Resend and renders the notice.
- Allowlist: `create_workspace_invitation` already inserts into `auth_invites`, so the before-user-created hook admits the invitee. No SQL change.

## Failure / security
- Mail send happens after the row exists; failures never roll back the invitation.
- Only owners/admins can resend (server-side check); the mailer only ever targets the invitation's stored address.
- Secrets: service-role key already read from server env; nothing new in the repo.
