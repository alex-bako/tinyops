# M3.T5 — Create-workspace form shares the same behavior

## Objective

A member who joined by invitation and creates her own workspace from the switcher
gets what the onboarding flow gives: a handle derived from the name until she takes
it over, the same format rule and messages, the same live availability answer, and a
handle taken at submit reported at the handle field instead of "Could not create
workspace." (OBI-10, D4.)

## Exclusions

- Workspace settings' handle editing, beyond what the shared rule changes incidentally.
- The onboarding flow itself (T1-T4, done).
- Any new migration. `create_personal_workspace`
  (`supabase/migrations/20260509003000_workspace_lifecycle_rpc.sql:31`) inserts straight
  into `public.workspaces` and lets the unique violation out untouched, which is exactly
  what `isWorkspaceHandleConflict` already reads.

## The decision worth recording

The form holds `name`, `handle` and `description` in three `useState`s and derives
nothing. The onboarding flow solves the same problem in a reducer with an `edited`
map. Copying the reducer here would be a second copy of a thing the person can only
see once; three `useState`s plus one `handleEdited` boolean is the whole of it:

```tsx
const [handleEdited, setHandleEdited] = React.useState(false)
const onName = (value: string) => {
  setName(value)
  if (!handleEdited) setHandle(deriveWorkspaceHandle(value))
}
```

The take-over re-arms the same way onboarding's does: an emptied handle goes back to
following the name (`setHandleEdited(value !== "")`), so a cleared field is not a dead
end. Everything else - `workspaceHandleIssue`, `WORKSPACE_HANDLE_MESSAGES`,
`useWorkspaceHandleAvailability`, the suggestion button - is imported, not rewritten.

## The silent substitution this slice is expected to settle

`workspaceHandleForStore` carries a `ponytail:` note saying so. `createWorkspace`
(`application.ts:150`) calls it as `workspaceHandleForStore(input.handle || name)`,
which substitutes `WORKSPACE_HANDLE_FALLBACK` when nothing survives normalization and
otherwise hands a too-short handle straight to the check constraint. Both outcomes are
the thing this milestone exists to stop: one stores a handle nobody asked for, the
other reports a database error for a rule the form could have said out loud.

So the create path switches to `normalizeWorkspaceHandle` - which returns `""` rather
than something unstorable - and an empty result becomes `invalid_workspace_handle`,
surfaced at the field like the taken handle. `workspaceHandleForStore` itself is left
alone: the other caller is not this slice's, and this change removes the only one that
the milestone's acceptance names.

## Implementation order

1. Store: `supabase-store.ts` `createWorkspace` names the collision (T4's predicate,
   imported - not re-derived). One store test.
2. Application: the two new `WorkspaceActionError` values and the switch off
   `workspaceHandleForStore`. Mapping tests in `application.test.ts`.
3. Form: derivation with take-over, the shared format rule, the availability hook,
   both field errors. `create-workspace-form.test.tsx` for the four acceptance
   examples, driven one change event per character as `type()` does in the onboarding
   test - a whole-value change is one keystroke and hides exactly the defect this
   milestone started from (OBI-12).

Steps 1 and 2 are one commit; the form is the second. Nothing here touches the
onboarding flow, so T4's tests must pass untouched.

## Failure behavior

- `createWorkspaceAction` returns `{ error: "workspace_handle_taken" }`: the message
  goes on the handle field, `aria-invalid`, and the name and description stay typed.
- Any other error keeps today's "Could not create workspace." sentence.
- The availability check failing (`unknown`) never disables the button (OBI-9).
- The button stays disabled while the handle is malformed or known taken, as on the
  onboarding step.

## What T4's review taught this slice

The onboarding form was repaired for three things the same form here would repeat.
They are requirements here, not discoveries to be made twice:

1. **A rejection is about a value, not about a field.** Clearing it on the next
   keystroke lets the person type the refused handle straight back in and submit it
   again - the availability hook has no reason to re-ask, because the handle it last
   saw was free. Keep the refused string and show the message exactly while
   `handle === rejectedValue`:

   ```tsx
   const [rejected, setRejected] = React.useState<string | null>(null)
   const takenHere = rejected !== null && handle === rejected
   ```

   `takenHere` is what disables the button and drives `aria-invalid`; no effect and no
   clearing anywhere.

2. **A rejection nobody can see is not reported.** This form does not move between
   steps, so focus is already near the field - but the message still needs to live in
   the element the input's `aria-describedby` points at, mounted before it has text,
   and the input still needs `aria-invalid`. Mirror `step-workspace.tsx`.

3. **The predicate reads `message` and nothing else, and matches the bare constraint
   name.** `isWorkspaceHandleConflict` is imported, not re-derived - reading `details`
   admits a false positive that no edit of the handle can clear, and matching Postgres'
   English sentence makes the whole thing depend on `lc_messages`.
   `create_personal_workspace` (`20260509003000_workspace_lifecycle_rpc.sql:31`) has no
   `exception when` block, only two `raise exception`s before the insert, so the raw
   `23505` and its constraint name arrive intact.
