# M3.T1 — Derived fields track their source

Objective: "How clients know you", the URL handle and the icon letter keep following the
fields they are derived from for as long as the person has not typed into them (OBI-1, A1,
the reported defect), and the component suite can no longer hide this class of bug because
it drives inputs one character at a time (OBI-12).

Exclusions: no handle validation, no minimum length, no availability check, no server or
migration change, no change to `create-workspace-form.tsx` (T2, T3, T4, T5 own those). The
handle input keeps its current silent character filter — replacing it is T2's job.

## Root cause (verified against current code 2026-09-18)

`apps/web/components/onboarding/onboarding-flow.tsx:76-94`. Each derive effect guards on
the field it writes:

```tsx
if (data.firstName && !data.senderName) { … }   // line 77
if (data.workspaceName && !data.handle) { … }   // line 85
```

The first keystroke makes the target non-empty, which makes the guard false forever. The
effect fires exactly once, so `Alex` + `Bakó` leaves `senderName` at `A`. The effect also
lists its own output in its dependency array (`data.senderName`, `data.handle`,
`data.iconLetter`), which is what forced the self-guard in the first place.

The suite does not catch it because every field is set with a single whole-value
`fireEvent.change` (`onboarding-flow.test.tsx:19-40`), which is one "keystroke" carrying
the final string.

## Design decision — derive in the reducer, delete the effects

M3.md described this slice as "per-field edited flags + the derive effects run on every
source change". Deriving inside the reducer is the same rule with a strictly smaller diff:
every write to `data` already goes through `dispatch({ type: "patch_data" })` — the three
effects are the only other writers, and they dispatch into the same reducer. Folding the
derivation into the `patch_data` branch removes all three `useEffect`s, removes the extra
render pass per keystroke, and removes the possibility of an effect reacting to its own
output. No new state shape beyond the `edited` map.

## Acceptance mapping

| Acceptance (M3.md) | Where |
| --- | --- |
| `A`,`l`,`e`,`x` then `B`,`a`,`k`,`ó` → sender name `Alex Bakó` after every keystroke | reducer derives on every `firstName`/`lastName` patch while `edited.senderName` is false |
| editing the sender name, then typing in Last name, leaves it unchanged | `patch_data` sets `edited.senderName = true` for a non-empty user value |
| clearing the sender name, then typing in First name, fills it again | `patch_data` sets `edited.senderName = false` for an empty user value; nothing re-derives until the next source patch, so the cleared field stays cleared |
| `Park Therapy` typed character by character → handle `park-therapy`, icon `P`; editing either stops it following | same rule keyed on `workspaceName` for `handle` and `iconLetter` |
| going Back and changing the name still updates an unedited sender name | step navigation does not touch `data` or `edited` |
| the suite drives one character at a time (OBI-12) | `type()` helper in `onboarding-flow.test.tsx`, existing whole-value writes rewritten to use it |

## Illustrative reducer branch (verify names against current lines 307-338)

```ts
case "patch_data": {
  const data = { ...state.data, ...action.patch }
  const edited = { ...state.edited }
  // ponytail: a field the person typed into stops following its source; emptying it
  // hands it back. Deriving here, not in an effect, is why it can react to every
  // keystroke instead of guarding on its own output.
  for (const key of Object.keys(action.patch) as (keyof OnboardingData)[]) {
    edited[key] = action.patch[key] !== ""
  }
  if (!edited.senderName && ("firstName" in action.patch || "lastName" in action.patch)) {
    data.senderName = `${data.firstName} ${data.lastName}`.trim()
  }
  if ("workspaceName" in action.patch) {
    if (!edited.handle) data.handle = slugify(data.workspaceName)
    if (!edited.iconLetter) {
      data.iconLetter = (data.workspaceName.trim()[0] ?? "").toUpperCase()
    }
  }
  if ("vertical" in action.patch) {
    const vertical = VERTICALS.find((v) => v.id === data.vertical)
    if (vertical) data.sensitivity = vertical.sensitivity
  }
  return { ...state, data, edited }
}
```

`edited` is `Partial<Record<keyof OnboardingData, boolean>>` on the flow state, not on
`OnboardingData` — `OnboardingData` is the shape `buildCommand` sends to the server and
must not grow UI bookkeeping.

Two details that are easy to get wrong:
- `data.workspaceName.trim()[0] ?? ""` — the current line 89 is `data.workspaceName[0]!`,
  which is only safe behind the `data.workspaceName &&` guard being removed here. A
  workspace name of `" "` must not throw.
- `slugify` here is the onboarding one (`./data`, keeps typed dashes, caps at 32), not
  `features/workspaces/use-cases.ts`. Reconciling the two is T2, not T1.

## Tests

```ts
// per-character typing: one change event per character, cumulative value
function type(field: HTMLElement, value: string) {
  for (let i = 1; i <= value.length; i++) {
    fireEvent.change(field, { target: { value: value.slice(0, i) } })
  }
}
```

Cases, all in `onboarding-flow.test.tsx`:
1. `type(firstName, "Alex")`, `type(lastName, "Bakó")` → sender name `Alex Bakó`.
2. after that, set the sender name to `Alex at Bako Studio`, then `type(lastName, "Bakos")`
   → sender name still `Alex at Bako Studio`.
3. clear the sender name → it stays empty; then type another character into First name →
   it fills from the source again.
4. `type(workspaceName, "Park Therapy")` → handle `park-therapy`, icon preview button `P`.
5. edit the handle to `park-clinic`, then `type(workspaceName, …)` more → handle stays
   `park-clinic`.
6. the two existing submit tests keep passing through `type()`, proving `buildCommand`
   still sends what the person saw.
7. `type(workspaceName, " Park Therapy")` with a leading space → the icon swatch pressed
   button is `P`. The leading space is the only input where the reducer's
   `workspaceName.trim()[0]` and `step-workspace.tsx`'s own `workspaceName[0]` fallback
   disagree, so this pins the derivation rather than the fallback; both uppercase, so a
   lowercase name would not distinguish them.
8. pick Coaching, then Therapy, on the vertical step → the sensitivity step lands on
   `Strict`. **Order matters.** Coaching's default is `balanced`, which is also
   `INITIAL_DATA.sensitivity`, so a therapy→coaching test asserting `Balanced` is
   satisfied by initial state and passes even with the whole vertical derivation deleted
   (finding M3T1-06). Coaching→Therapy asserting `Strict` fails under *both* mutations:
   deleting the derivation, and flipping the guard to `!state.data.vertical`.

Mutation rule for this slice: a test whose expected value equals the corresponding
`INITIAL_DATA` default pins nothing until it is verified against *deletion* of the
derivation, not only against a flip of its guard. Flipping the guard alone is what let
M3T1-05 be recorded as pinned when it was half pinned.

## Failure / security

No trust boundary is crossed: this is client state only, and the server still normalizes
and validates in `features/onboarding/application.ts`. The one behavior change visible to
the server is that `workspaceHandle` and `senderName` now carry the full derived value
instead of a one-character truncation — strictly closer to what the person saw.

## Migration / rollback

None. Revert is a single-file revert.

## Risks / unresolved

- Marking `edited` for every patched key also flags `iconTone`, `vertical`, `invites` and
  the IMAP fields. Nothing reads those flags; kept uniform rather than maintaining an
  allow-list.
- The vertical → sensitivity rule moves from an effect into the reducer. Current behavior
  (picking a vertical always overwrites sensitivity, a later manual sensitivity choice
  survives until the vertical changes again) must be preserved; case 6 of the existing
  suite covers `sensitivity: "strict"` reaching `completeOnboarding`.
- `slugify("Park ")` → `park` (it trims before substituting dashes), so a trailing space
  does not produce a trailing dash. Asserted implicitly by case 4.
