# M3.T4 — Server validation failures reach their field

Slice of [M3](../roadmap/milestones/M3.md). Depends on T2 (the shared handle rule)
and lands on top of T3 (`8b6f75b`, live availability).

## Objective

A person who reaches the last screen and is still rejected by the server is put back
on the step holding the offending field, with the message on that field and every
other answer intact (OBI-8). Today every store failure collapses into one sentence
under the Open TinyOps button, and a handle taken between the availability answer and
submit is indistinguishable from a database outage.

**Excludes**: the create-workspace form (T5). Invite-row errors keep the generic
banner — routing to one row of a list is its own problem and no acceptance example
asks for it.

## The one decision worth recording

The milestone says the store "distinguishes a handle unique violation (Postgres
`23505` on the handle index)". Reading the RPC shows `23505` is *not* on its own
enough: `complete_onboarding` also raises `duplicate_invite` with `errcode = '23505'`
(migration `20260510000000`, line 226), and so do six other RPCs in this repo. A bare
code test would tell a person their handle was taken when their colleague's email was
the duplicate.

Two ways out:

1. Teach the RPC to name it: wrap the `insert into public.workspaces` in an exception
   handler that re-raises `workspace_handle_taken`. This is the house idiom — every
   other expected failure in these functions is a named message that `mapWorkspaceActionError`
   and `throwWorkspaceStoreError` match by name.
2. Recognize the raw violation client-side: `23505` **and** the failing constraint is
   the one on `workspaces.handle`.

Taking (2). (1) is the nicer contract but costs a migration that restates the whole
250-line `complete_onboarding` body — a large, permanently-forked copy of SQL that
this slice changes nothing else about, and the same again for `create_personal_workspace`
in T5. (2) is about fifteen lines and serves both call sites.

The cost of (2) is a dependency on the constraint name, which a fixture-based unit
test cannot notice going stale. That is paid for with a psql contract case that
provokes a real collision and asserts the SQLSTATE and the constraint name, so the
thing the TypeScript matches on is pinned in the database where it lives.

## Implementation order

1. `handle-conflict.ts` + its test. Nothing else can be right if this is wrong.
2. Store, then application: the error acquires a name and survives the seam.
3. Flow routing, then the two steps' rendering.
4. The psql contract case.

### The predicate

```ts
// Illustrative. A unique violation says which constraint it was; `23505` alone does
// not, because `complete_onboarding` raises `duplicate_invite` with the same code.
export function isWorkspaceHandleConflict(cause: unknown): boolean
```

Matched against `code === "23505"` and the constraint named in the Postgres message.

### The routing table

```ts
// Illustrative.
const ERROR_FIELD: Partial<
  Record<OnboardingValidationError, { step: StepId; field: keyof OnboardingData; message: string }>
> = {
  first_name_required: { step: "name", field: "firstName", message: "Enter your first name." },
  workspace_name_required: { step: "workspace", field: "workspaceName", message: "Enter a workspace name." },
  workspace_handle_required: { step: "workspace", field: "handle", message: WORKSPACE_HANDLE_MESSAGES.required },
  workspace_handle_taken: { step: "workspace", field: "handle", message: "That handle was just taken." },
}
```

An error absent from the table keeps today's banner. That is the milestone's "the
generic banner remains only for genuinely unattributable failures".

### Two invariants the tests have to hold down

**The stale "free" answer.** Landing back on Workspace does not change `data.handle`,
so `useWorkspaceHandleAvailability` never re-runs and keeps saying *free* — the very
answer that let the submit through. Continue would therefore be enabled on a handle
the server has just refused. `canContinue` for the workspace step must also fail while
a handle field error is showing.

**Clearing.** The field error survives until the person edits that field, and only
that field. Editing the workspace name clears the name's error, not a handle error
the same step is showing.

## Failure and security behavior

No trust boundary moves. The server action still decides everything; the flow only
chooses where to *display* what it is told. A `workspace_handle_taken` invented by a
client buys nothing — the RPC's unique index is what actually refuses the write.

## Risks

- **Constraint rename.** Mitigated by the psql case, not by the unit test.
- **A second raw unique violation inside the RPC.** The other inserts are into a
  workspace created moments earlier by the same transaction, so nothing pre-existing
  can collide there; `duplicate_invite` is pre-checked and named.
- **Answers lost on the way back.** The reducer only moves `stepIdx` and sets the
  error; `data` is not touched. The test asserts the command re-sent after the fix is
  the same one apart from the handle.
