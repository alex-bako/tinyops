# Plan — M1.T3 Copy invite link

## Objective
An owner/admin copies a sign-in link for a pending invitation and sends it however they like; the invitee opens it and lands on Join (INV-5). No email involved.

## Acceptance mapping (docs/roadmap/milestones/M1.md → checks)
- Pending invite + Copy link → clipboard holds a Supabase action link with redirect `/auth/callback?next=/join` → `invite-mailer.test.ts` (link generation), `section-members.test.tsx` (button → command).
- Expired link → existing `/login?auth=expired` (unchanged); clicking Copy link again generates a fresh link → generateLink is idempotent per call.
- Viewer/operator → no Copy link (button hidden/disabled) and the server action rejects with `invite_forbidden` → `application.test.ts`.
- Revoked/accepted invite → not in `workspace.invites`, action returns `invite_not_found` → `application.test.ts`.
- Also folds review advisory N1 from T2: the invite notice renders even when there are no pending rows.

## Design (ponytail)
- Extend the existing delivery port in `invite-mailer.ts` with `createInviteLink({ email }) → { link | null, error }` using `admin.auth.admin.generateLink({ type: "invite", email, options: { redirectTo } })`, falling back to `type: "magiclink"` on `email_exists` (same rule as sendInvite, single account per person).
- Application: `createInviteLink(invitationId)` → `{ link } | { error }` (owner/admin, pending only). Server action `createWorkspaceInviteLinkAction`.
- Context: `copyInviteLink(invitationId)` calls the action then `navigator.clipboard.writeText`; notice kinds `link_copied` / `failed`.
- UI: "Copy link" button on each pending row (owners/admins).

## Folded defect (found during the T3 live check)
Admin-generated links (`generateLink`, `inviteUserByEmail`, server-side `signInWithOtp`) have no PKCE verifier in the invitee's browser, so Supabase's verify endpoint redirected with tokens in a URL fragment and `/auth/callback` (which only knew `?code=`) sent invitees to `/login?auth=expired`. This broke T2's emails as well. Fix: the callback also accepts `token_hash` + `type` (`invite`/`magiclink`) via `verifyOtp`; the copy link and the local email templates (`supabase/templates/*.html`) build that URL; `buildAuthCallbackUrl` always carries `next` so templates can append with `&`.

## Failure / security
- The link is a real sign-in credential for the invited address: only owners/admins may generate it, it is never stored, and it only ever targets the stored invitation email.
- Redirect is built by `buildAuthCallbackUrl` (safe `next`) and must be in the Supabase redirect allowlist (documented in M1.S1).
