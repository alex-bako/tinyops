# M2.T1 — Workspace list means memberships only

Objective: `listWorkspaces()` returns only workspaces the actor has a `workspace_memberships` row in, so a fresh invitee is routed to Join instead of Home → Onboarding (INV-3, INV-12, conflict C1). Exclusions: no policy or migration change (the Join screen still needs the invitee policy); no switcher or create-workspace changes (INV-13 is an exit-gate check per D2); no onboarding flow changes.

## Root cause (verified live 2026-09-18)
As the invitee, `select … from workspaces` returns the invited workspace with `workspace_memberships: []` because policy "Invitees can read invited workspaces" (migration `20260918000100`) satisfies RLS. `app/join/page.tsx` treats `workspaces.length > 0` as "member" → `/home` → `(app)/layout.tsx` sends the un-onboarded profile to `/onboarding`.

## Illustrative change (verify against current lines 112–124)
```ts
// ponytail: RLS also shows invitees the workspace they were invited to (Join
// screen). "My workspaces" means memberships, so drop rows without ours.
return ((data ?? []) as WorkspaceRow[])
  .filter((row) =>
    row.workspace_memberships?.some((m) => m.user_id === actorUserId)
  )
  .map((row) => mapWorkspaceRow(row, { userId: actorUserId }))
```
Why in JS and not the query: a PostgREST `workspace_memberships!inner` + `.eq("workspace_memberships.user_id", …)` would also narrow the embedded members list to the actor, breaking the Members page which reads `members` from the same rows. Owners and members can read all membership rows of their workspaces ("Members can read workspace memberships"), so their own row is always present; the invitee reads none.

## Implementation order

## Failure / security
- No trust-boundary change; RLS still gates what rows arrive. The filter only tightens what the app calls "mine".
- If a member's own membership row were ever hidden by RLS, they would vanish from their own list. Covered: the membership read policy grants members all rows of their workspaces; the SQL contract asserts member reads.
