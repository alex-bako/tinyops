# M3.T2 — One normalization rule and handle field errors

Objective: the handle a person sees is the handle that will be stored, and a handle that
is too short, too long or ends with a dash is reported at its own field before Continue
becomes available (OBI-2, OBI-3, OBI-4). One module owns the rule; the two divergent
`slugify` implementations are deleted.

Exclusions: no availability check and no suggestion (T3), no submit-time collision routing
(T4), no change to `create-workspace-form.tsx`'s UI (T5), no migration, nothing that needs
the database.

## Root cause (verified against current code 2026-09-18)

Three rules disagree today, which is why what the person sees is not what gets stored.

| Where | Rule | Consequence |
| --- | --- | --- |
| `components/onboarding/steps/step-workspace.tsx:73` | `e.target.value.replace(/[^a-z0-9-]/g, "")` | Typing `Park` **deletes** the `P` instead of lowercasing it → `ark` (the reported defect). |
| `components/onboarding/data.tsx:235-242` | lowercase → trim → `[^a-z0-9-]+`→`-` → strip end dashes → `slice(0, 32)` | Caps at **32**, keeps runs of existing dashes. |
| `features/workspaces/use-cases.ts:320-328` | trim → lowercase → `[^a-z0-9]+`→`-` → strip end dashes → `|| "workspace"` | **No cap at all**, so a long name reaches the DB check constraint; falls back to `"workspace"`. |

The database constraint (`supabase/migrations/20260509001000_workspaces.sql:21-24`) is the
only real authority:

```sql
constraint workspaces_handle_normalized check (
  handle = lower(btrim(handle))
  and handle ~ '^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$'
)
```

That regex means: length 3–64, first and last character alphanumeric. We cap at **63** so
a handle can never be rejected for length.

There is no field-level feedback anywhere: `canContinue` (`onboarding-flow.tsx:87-90`) only
checks that the handle is non-empty, so `pa` passes the UI and is rejected server-side by
`normalizeCommand`'s `handle.length < 3` (`features/onboarding/application.ts:264`).

## Design decision — one rule, four entry points

A single `slugify` cannot serve all three callers, which is why the two existing ones
diverged. The behaviours genuinely differ in one respect only — what happens to a **trailing
dash** — so the module is one core plus two thin wrappers:

- `sanitizeWorkspaceHandleInput(raw)` — for the handle **field**. A trailing dash is kept,
  because the person may be typing past it; a leading dash is dropped, because it can never
  become valid. This is what makes `park-clinic` typeable character by character.
- `deriveWorkspaceHandle(name)` — for the handle derived from the **workspace name**. Same
  rule, trailing dash stripped: nothing is being typed at the end, so `Park ` must show
  `park`, not flash "cannot end with a dash" on the space.
- `normalizeWorkspaceHandle(value)` — for **storage**. `deriveWorkspaceHandle`, then `""`
  when the result is shorter than 3. Returning `""` rather than a too-short string is what
  makes the property in M3.md literally true and keeps the server's existing
  `workspace_handle_required` branch working unchanged.

### Ambiguity resolved

M3.md's acceptance reads: "Typing `--park--` yields `park`; typing `p` `a` `r` `k` `-`
yields `park-` **in the field**". Those two cannot both describe the handle field under one
rule. Read as written — the second clause says "in the field" and the first does not — the
first is the **derivation** from the workspace name and the second is direct typing into the
handle field. Both are tested, under that reading:

- workspace name `--park--` → handle `park`
- handle field `--park--` → `park-` with "A handle cannot end with a dash"

### The `"workspace"` fallback is preserved, not fixed

`use-cases.ts` and `application.ts` today turn an unusable handle into `"workspace"`.
Silently renaming someone's workspace is a real wart, but it is pre-existing, not listed in
M3, and changing it needs a new `WorkspaceActionError` value — that belongs with T5's form
work. So it is kept **bug-for-bug**, via `workspaceHandleForStore`.

Bug-for-bug is a stronger claim than it first looks, and the first implementation got it
wrong. Both review seats independently caught it:

- The deleted `slugify` returned a 1–2 character result **as-is** (`"ab"` → `"ab"`), which
  then hit the check constraint and failed loudly with the handle intact. Routing that call
  site through `normalizeWorkspaceHandle` (which returns `""` below the minimum) turned that
  loud failure into a silent rename to `"workspace"`. The settings form resubmits the whole
  draft on every save, so this reached **live** workspaces, not just new ones.
- The deleted `slugify` had no length cap. Applying the new 63-character cap to a handle the
  person never touched would rewrite a legacy 64-character handle on any unrelated settings
  save, contradicting M3.md's "Existing rows are not touched (A6)".

Round two caught a third way to get it wrong, in the fix for the second. Returning a
DB-valid value *untouched* skips more than the cap: the constraint permits `ab--cd`, which
`slugify` — and every other entry point — collapses to `ab-cd`. So the pass-through now
protects exactly the one thing derivation would damage, the length:

- `isStoredWorkspaceHandle(value)` — the database regex verbatim. Such a value keeps its own
  length instead of being capped, so no existing row is shortened; it still gets the rest of
  the rule, which for a stored handle means collapsing dash runs and nothing else.
- `workspaceHandleForStore(value)` — derive, **keep** a too-short result so the database
  rejects it as it always has, and substitute only when nothing is left at all.

The net effect is `slugify` reproduced exactly, plus the 63-character cap on values that are
not already stored. `normalizeWorkspaceHandle` keeps returning `""` below the minimum,
because onboarding's `normalizeCommand` wants exactly that: a validation error, not a
substitution.

## Illustrative module (verify against the file as written)

```ts
export const HANDLE_MIN_LENGTH = 3
export const HANDLE_MAX_LENGTH = 63
export const WORKSPACE_HANDLE_FALLBACK = "workspace"

export function sanitizeWorkspaceHandleInput(value: string) {
  return value
    .toLowerCase()
    .replace(/[^a-z0-9]+/g, "-") // any run of punctuation or dashes becomes one dash
    .replace(/^-+/, "") //           a leading dash can never become valid
    .slice(0, HANDLE_MAX_LENGTH)
}

export function deriveWorkspaceHandle(value: string) {
  return sanitizeWorkspaceHandleInput(value).replace(/-+$/, "")
}

export function normalizeWorkspaceHandle(value: string) {
  const handle = deriveWorkspaceHandle(value)
  return handle.length < HANDLE_MIN_LENGTH ? "" : handle
}
```

Issues are a closed set; only `at_max_length` is advisory:

```ts
export type WorkspaceHandleIssue =
  | "required"
  | "too_short"
  | "trailing_dash"
  | "at_max_length"
```

## Failure / security

No new trust boundary. The module is pure and dependency-free. The server keeps validating
independently of the client: `normalizeCommand` still rejects an unusable handle, and the DB
check constraint remains the last word. No secrets, no network.

## Migration / rollback

None. No schema change. Rollback is reverting the commit; no data is written in a new shape,
because the handles this produces are a strict subset of what the constraint already allowed.

## Risks / unresolved

- Capping at 63 where onboarding capped at 32 means newly derived handles can be longer than
  any existing one. The constraint already permitted 64, so nothing existing breaks.
- `mock-client-memory.ts` has its own unrelated `slugify` for client IDs. Out of scope —
  different purpose, different output space, no workspace handle involved.
- The `"workspace"` fallback survives this slice by design (see above).
- **`workspaceHandleForStore` is not DB-safe by construction, deliberately.** A fuzz over
  319,104 inputs returns a value the check constraint rejects for 64,855 of them (`"aa-"` →
  `"aa"`, `"9"` → `"9"`), because keeping a short handle is the whole point — the database
  rejects it loudly, as it always did. Nothing may reuse this function assuming a storable
  result. T5 is where that becomes a field-level error instead. `normalizeWorkspaceHandle`
  *is* DB-safe (0 violations over the same corpus); use that one when a storable-or-nothing
  answer is wanted.

## Review outcome

Two rounds against a frozen diff. Round one raised six findings; fixing two of them
introduced a seventh, which round two caught. All dispositioned:

| Finding | Disposition |
| --- | --- |
| `handle-fallback-clobbers-short-handle` (blocking) — silent rename of a live workspace on the settings save path | **resolved**: `workspaceHandleForStore` keeps the short handle; pinned by `use-cases.test.ts` |
| `handle-cap-truncates-existing-64` — legacy 64-character handle rewritten on an unrelated save | **resolved**: `isStoredWorkspaceHandle` pass-through; pinned by `handle.test.ts` and `use-cases.test.ts` |
| `edited-flag-uses-raw-patch` — a keystroke that sanitizes to nothing stranded the field | **resolved**: the flag now reads the sanitized value |
| `empty-handle-has-no-feedback` — `required` was unreachable in the UI | **resolved**: shown once there is a workspace name |
| `alert-role-added-with-content` — a role appearing with its own text is not reliably announced | **resolved**: one permanently mounted `role="status"`; `aria-invalid` carries the error state |
| `fallback-substitution-behavior-change` (cross-model, same root cause as the first) | **resolved** by the same change |
| `stored-handle-shortcircuit-skips-dash-collapse` (cross-model, blocking, round 2 — introduced by the fix for `handle-cap-truncates-existing-64`) — `ab--cd` stored verbatim where `slugify` gave `ab-cd` | **resolved**: the pass-through now skips the cap only, not the whole rule; pinned by `handle.test.ts` |
| `handle-table-agreement-test-blind-to-shortcircuit` (cross-model, round 2) — no table row could reach the fast path | **resolved**: `ab--cd` added to `HANDLE_TABLE`; removing the fix fails all three entry points' agreement tests |
| `passthrough-skips-documented-63-cap` (specialist, round 2, doc-only) — the module header still claimed an unconditional cap | **resolved**: header rewritten |
| `store-helper-not-db-safe-undocumented` (specialist, round 2, doc-only) | **resolved**: recorded under Risks above |

The cross-model seat additionally confirmed no T3/T4/T5 scope leaked in, and that the only
remaining `slugify` in the repo is `mock-client-memory.ts`'s unrelated client-ID one. The
specialist seat re-fuzzed 319,104 inputs against `normalizeWorkspaceHandle` with zero
constraint violations, and verified that every field value `canContinue` accepts passes
through both server functions unchanged.
