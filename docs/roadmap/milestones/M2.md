# M2 — Invitee lands in Join, not Onboarding

## User outcome and exit gate

Outcome: a person with no TinyOps account follows an invite link, sees the Join screen, accepts, and is a member of exactly that workspace. She was never asked to create a workspace. Later she can create her own workspace from the switcher and keep both.

Exit gate (observable, local stack then staging): invite a fresh address from Settings → Members, open the Mailpit/real link, and the first screen is Join with the workspace name and role. After Accept, Home shows only that workspace. Then, as that member, use the switcher's "Create or join a workspace" entry: a second workspace is created, she owns it, the original membership is untouched, and no onboarding step appears (INV-13, D2).

## Scope and non-goals

In scope: INV-12 (defect C1) and INV-13 acceptance. Non-goals: founder onboarding questions for a second workspace (rejected in D2), any change to roles or seats.

- Verified 2026-09-18 on the local stack: as the invitee, `select … from workspaces` returns the invited workspace with an empty `workspace_memberships` embed. The fix belongs in the store (list only rows where the actor has a membership), not in the policy, which the Join screen still needs.

## Tracer bullets (ordered)

### M2.T1 — Workspace list means memberships only

- **Scenario**: a signed-in invitee with a pending invitation and no membership opens the invite link and sees Join, not Onboarding (INV-3, INV-12).
- **End-to-end boundary**: `listWorkspaces` in the Supabase store filters to workspaces where the actor has a membership → `/join` sees no workspaces and renders the Join flow → Accept → Home. Members and owners see the same list as before.
- **Depends on**: nothing inside M2. **Owner**: coordinator + one builder.
- **Acceptance examples**:
  - Given VA has a pending invitation to Ada's Studio and no membership, when the auth callback redirects to `/join`, then the Join screen shows "Ada's Studio · Operator" and no redirect to `/home` or `/onboarding` happens.
  - Given Ben is a member of two workspaces and invited to a third, when Home loads, then the switcher lists two workspaces and one invitation.
  - A store test proves an invitee-visible workspace without a membership row is excluded from `listWorkspaces`; the existing SQL contract for the invitee policy still passes.
- **Verification**: web tests for the store and Join page, typecheck, lint, plus the local browser run through Mailpit as in the exit gate.
