# M1 — Invite a person into a workspace

## User outcome and exit gate

Outcome: an owner sends an invite from Settings → Members; the invitee, with no prior TinyOps account and no Supabase organisation membership, receives an email, clicks it, enters their name and is inside the owner's workspace with the invited role. Email failure is survivable through a copyable link.

Exit gate (observable, on staging): perform the flow above with a real non-organisation address; the new member appears in the Members list, the pending invite disappears, and the invitee's first screen is the invited workspace, not onboarding. Revoked-invite and wrong-address negative cases behave as the domain invariants say.

## Risks and material decisions

- **Decided (D1)**: email and copy-link both.
- **Assumed (A2)**: copy-link is a Supabase admin-generated sign-in link. Risk: a leaked link signs in the invitee's address until expiry. Mitigation: shown only to owners/admins for pending invites, address-bound, expires, regenerable.
- **Assumed (A5)**: SMTP is configured by the user on hosted Supabase. Risk: without it, T2 works locally (Mailpit/Inbucket) but not on staging. That is why S1 is a gate for milestone exit.
- Existing users vs new users need different Supabase calls to send mail (invite vs magic link). Detail settled in `aw-plan` for T2.
- `accept_workspace_invitation` does not mark the profile onboarded; T1 must decide whether to extend the RPC or add a sibling. Prefer one RPC that does both atomically.

## Tracer bullets (ordered)

### M1.T1 — Invitee Join flow (first slice)

- **Scenario**: a signed-in user with a pending invitation and no membership sees the Join flow, enters their name, accepts and lands in the workspace (INV-3, INV-4, INV-8 message).
- **End-to-end boundary**: app layout / onboarding routing → new Join page → server action → RPC that accepts the invitation and marks the profile onboarded → redirect to `/home` with the joined workspace active.
- **Depends on**: nothing. **Owner**: coordinator + one builder.
- **Acceptance examples**:
  - Given VA has a pending invitation and no membership, when they open `/home`, then they see Join with the workspace name and role, not the onboarding "Your name / Your work" steps.
  - Given they submit first name "Mia" and Accept, then a membership with the invited role exists, `profiles.onboarded_at` is set, the invitation is accepted, and the response redirects to the workspace.
  - Given the invitation was revoked before Accept, then Join shows "This invite is no longer valid" and no membership is created.
  - Given a user with an existing membership, then routing is unchanged (no Join interception); the pending invitation stays visible in the switcher (INV-11).
  - Given an existing Auth user with no membership and a pending invitation (onboarding never finished), then Join is shown and accepting attaches the membership to that same user; no new user or profile row is created (INV-11).
  - Given no pending invitation and no membership, then onboarding runs as today.
- **Verification**: vitest for routing decision and use-case (pure functions with fake store), SQL contract test for the RPC (accept + onboarded, revoked case, email mismatch, invitee can read the invited workspace), `onboarding/page.test.tsx` and `join/page.test.tsx` for the routing decision, `join-flow.test.tsx` for the component. Manual local run with a seeded invitation.
- **Exclusions**: no email, no copy-link, no switcher changes.
- **First sources**: `apps/web/app/(app)/layout.tsx`, `apps/web/app/onboarding/page.tsx`, `apps/web/features/workspaces/use-cases.ts` (`listJoinableWorkspaces`, accept), `supabase/migrations/20260509003000_workspace_lifecycle_rpc.sql` (`accept_workspace_invitation`), `supabase/tests/workspace_rpc_contract.sql`.

### M1.T2 — Invite email on create and Resend

- **Scenario**: creating an invitation sends the invitee an email with a link that lands on Join; Resend sends it again; send failure leaves the invitation saved and tells the inviter (INV-2, INV-6, INV-7 email part).
- **End-to-end boundary**: Members page → invite/resend server actions → workspace application → a mail-sending port implemented with the Supabase admin Auth client (invite for new users, magic link for existing users), redirect target = auth callback with `next=` Join → email → callback → Join (T1).
- **Depends on**: M1.T1.
- **Acceptance examples**:
  - Given a new address, when invited, then a Supabase invite email is sent with a link whose callback `next` is the Join path, and the row shows "Invited just now".
  - Given an existing TinyOps user's address, when invited, then a magic-link email is sent (never `inviteUserByEmail`, which fails for existing users) and, after sign-in, the switcher shows the invitation; the user keeps their single account (INV-11).
  - Given the Auth send call fails, then the invitation still exists and the UI shows "Invite saved, email not sent" without throwing.
  - Given a pending invite, when Resend is clicked, then another email is sent and the button is briefly disabled; revoked/accepted rows have no Resend.
  - Locally: emails are visible in the local Supabase mail viewer.
- **Verification**: vitest on the application with a fake mailer (success, failure, existing vs new user branch), UI test for the saved-not-sent state, manual local check through the mail viewer.
- **Exclusions**: no custom email templates in the repo beyond what local config needs; no copy-link.
- **First sources**: `apps/web/features/workspaces/application.ts` (`inviteMember`), `apps/web/features/workspaces/actions.ts`, `apps/web/lib/supabase/admin.ts`, `apps/web/lib/auth/route-policy.ts` (`buildAuthCallbackUrl`), `section-members.tsx` (Resend), `supabase/config.toml` (`[auth.email]`, templates).

### M1.T3 — Copy invite link

- **Scenario**: an owner/admin copies a sign-in link for a pending invite and sends it however they like; the invitee opens it and lands on Join (INV-5).
- **End-to-end boundary**: pending row → server action → Supabase admin generate-link for the invited address with the Join `next` → link returned to the client and copied → invitee opens it → callback → Join (T1).
- **Depends on**: M1.T1. Independent of T2.
- **Acceptance examples**:
  - Given a pending invite, when "Copy link" is clicked, then the clipboard holds a link that, opened in a fresh browser, signs in the invited address and shows Join.
  - Given the link is opened after expiry, then the existing "link expired" login message appears; the invite remains pending and can be regenerated.
  - Given a viewer/operator, then no Copy link is offered (server action rejects too).
  - Given a revoked invite, then no link can be generated.
- **Verification**: vitest for the action's permission and state checks with a fake link generator; manual local check.
- **Exclusions**: no shortener, no public share pages.
- **First sources**: `section-members.tsx`, `apps/web/features/workspaces/actions.ts`, `apps/web/lib/supabase/admin.ts`, `apps/web/features/workspaces/policy.ts`.

### M1.S1 — Hosted email delivery (spike/ops)

- **Scenario**: an invite email reaches a non-organisation address on staging (INV-9).
- **Work**: user configures custom SMTP on the staging (then production) Supabase project, sets invite and magic-link templates, and confirms the auth callback URL is in the redirect allowlist. Repo change limited to a short section in `docs/deployment.md`.
- **Depends on**: nothing in code; T2 is needed to send from the app, but a manual Supabase dashboard "invite user" can prove delivery first.
- **Exit evidence**: an email delivered to a non-organisation mailbox on staging, and the T2 flow completing there. Secrets stay outside the repo and are entered by the user.
- **Exclusions**: no production cut-over decision here.
