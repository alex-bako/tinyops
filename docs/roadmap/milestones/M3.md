# M3 — Onboarding fields that keep up and speak up

## User outcome and exit gate

Outcome: a founder types their name and workspace name and the derived fields follow every keystroke until they take one over. A handle that is too short, malformed, or already owned by another workspace is reported under the handle field while they are looking at it, with a free alternative offered in one click. No validation failure ever appears for the first time as an unexplained sentence on the final screen. An invited member creating her own workspace from the switcher gets exactly the same behavior.

Exit gate (observable, local stack, driven by hand in a browser after the suite is green):

1. On "Your name", type `Alex` then `Bakó`. "How clients know you" reads `Alex Bakó`, not `A`. Overwrite it with `Alex at Bako Studio`, type another character in Last name: the sender name does not change.
2. On "Workspace", type `Park Therapy`. The handle field reads `park-therapy` and the icon preview `P`. Clear the workspace name and type `Bako Studio`: the handle follows to `bako-studio`. Edit the handle by hand, then keep typing in the name: the handle does not change.
3. Type `Pa` as the workspace name: the handle field says a handle needs at least 3 characters and Continue is unavailable. The workspace name field says nothing, because names are free-form (OBI-11).
4. With a workspace already holding `park-therapy` (seeded), type a name deriving to it: the handle field says it is taken, offers `park-therapy-2`, and one click accepts it. Continue becomes available.
5. Type `Park` directly into the handle field: it becomes `park`, not `ark`.
6. Force a submit-time collision (take the handle in a second session between the check and Continue): the flow returns to the Workspace step with "just taken" on the handle field, and the name, vertical, sensitivity and source answers are all still there.
7. Stop the local Supabase stack, type a handle: the field says availability could not be checked and Continue stays available.
8. As a member who joined by invitation, open the switcher's "Create workspace": steps 2 through 6 behave identically there.

## Scope and non-goals

In scope: OBI-1 through OBI-12 across the onboarding flow and the switcher's create-workspace form.

Non-goals: any change to what onboarding asks or creates (OBI-13); workspace name uniqueness or length, which stay free-form (OBI-11, D2); silent server-side handle deduplication (D2); changing the handle format or the `workspaces_handle_normalized` constraint; reserved-word blocklists; rate limiting the availability RPC beyond requiring authentication (D3's accepted tradeoff); backfilling existing workspaces (A6).

## Risks and material decisions

- **Decided (D1)**: derive-until-edited. This needs an explicit per-field "the person edited this" flag in the flow state. Inferring it from "the field is non-empty" is precisely the current defect and must not be reintroduced; clearing a derived field re-arms it (OBI-1).
- **Decided (D3)**: live checking. Accepted tradeoff: an authenticated user can probe handle existence. The RPC therefore returns a boolean and nothing else (OBI-7), and is granted to `authenticated` only (A4).
- **Risk**: the two `slugify` implementations differ, so "unify them" changes the handle produced by the *existing* create-workspace path (dashes typed by a person survive in one and not the other). T2 must pick one rule, state it, and cover the divergent cases with tests. Existing rows are not touched (A6).
- **Risk**: neither implementation enforces the 63-character ceiling that the database check constraint applies. A long workspace name currently fails as a generic error; T2 must cap and say so.
- **Risk**: live checking introduces stale responses. The displayed answer must be keyed to the handle currently in the field, not to the last response that arrived (OBI-5). This is the most likely place for a defect that a test written after the fact would not catch — write the out-of-order test first.
- **Risk**: `@testing-library/user-event` is not installed, and the existing suite passes because it sets whole field values in one event. Every test in this milestone types character by character via repeated `change` events (A5); a test that sets a whole value proves nothing here.
- **Open, deferred to implementation**: the debounce interval. Start at 300 ms and confirm against the local stack; it is a constant, not a design decision.

## Tracer bullets (ordered)

### M3.T1 — Derived fields track their source

- **Scenario**: a founder types a first and last name and sees their full name in "How clients know you"; typing a workspace name fills the handle and icon letter the same way (OBI-1, A1, the reported defect).
- **End-to-end boundary**: the onboarding flow state gains per-field "edited by the person" flags → the derive effects in `onboarding-flow.tsx` run on every source change while the flag is clear → `StepName` and `StepWorkspace` render the derived values → `buildCommand` sends what was shown. No server, no database.
- **Depends on**: nothing. **Owner**: coordinator + one builder.
- **Acceptance examples**:
  - Typing `A`, `l`, `e`, `x` in First name then `B`, `a`, `k`, `ó` in Last name leaves the sender name reading `Alex Bakó` after every keystroke.
  - Editing the sender name to `Alex at Bako Studio` and then typing in Last name leaves the sender name unchanged.
  - Clearing the sender name entirely and typing in First name fills it again.
  - Typing `Park Therapy` character by character leaves the handle at `park-therapy` and the icon preview at `P`; editing the handle stops it following. The icon letter has no field of its own, so it always follows the workspace name; there is nothing to stop.
  - Going back to the name step and changing the name, without having edited the sender name, still updates it.
- **Verification**: `apps/web/components/onboarding/onboarding-flow.test.tsx` extended with a `type()` helper that fires one `change` per character; the existing whole-value assertions are rewritten to use it so the suite can no longer hide this class of defect (OBI-12). `pnpm --filter web test`, `typecheck`, `lint`.
- **Excludes**: validation, availability, the create-workspace form.

### M3.T2 — One normalization rule and handle field errors

- **Scenario**: a person typing a handle that is too short, too long or oddly punctuated is told at the field, and the handle they see is the handle that will be stored (OBI-2, OBI-3, OBI-4).
- **End-to-end boundary**: one shared normalization + validation module under `apps/web/features/workspaces` → imported by `onboarding-flow.tsx`/`StepWorkspace` for derivation, field state and `canContinue`, and by `features/onboarding/application.ts` and `features/workspaces/use-cases.ts` on the server so both sides agree → the existing `slugify` in `components/onboarding/data.tsx` and the one in `use-cases.ts` are deleted in favour of it.
- **Depends on**: nothing inside M3 (independent of T1; both touch `onboarding-flow.tsx`, so sequence them). **Owner**: coordinator + one builder.
- **Acceptance examples**:
  - `Pa` → handle `pa` → "A handle needs at least 3 characters." under the field, Continue unavailable, nothing shown on the workspace name field.
  - A 70-character name → the handle is capped at 63 and the field says so, rather than reaching the database check constraint.
  - Typing `Park` directly into the handle field yields `park`, not `ark`.
  - Typing `--park--` yields `park`; typing `p` `a` `r` `k` `-` yields `park-` in the field with "A handle cannot end with a dash" and Continue unavailable — the trailing dash is not silently eaten mid-typing.
  - The shared function and the database constraint agree: a property-style test asserts every non-empty normalized output matches `^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$`.
  - `normalizeCommand` and `createWorkspace` produce the same handle as the UI for the same input, proven by a test that runs both over one table of inputs.
- **Verification**: unit tests for the shared module, updated `onboarding-flow.test.tsx`, `features/onboarding/application.test.ts` and `features/workspaces/use-cases.test.ts`. `pnpm --filter web test`, `typecheck`, `lint`.
- **Excludes**: anything needing the database; the create-workspace form's UI (T5).

### M3.T3 — Live availability check and suggestion

- **Scenario**: a person typing a workspace name learns, while typing, that the derived handle is taken, and takes the offered free alternative in one click (OBI-5, OBI-6, OBI-7, OBI-9, A2, A3).
- **End-to-end boundary**: a new `security definer` RPC returning a boolean for one normalized handle, granted to `authenticated` only → a server action wrapping it → a debounced hook in the shared module that discards answers not matching the current field value → `StepWorkspace` renders available / taken + suggestion / could-not-check → `canContinue` requires "known free or unknown", never "known taken".
- **Depends on**: T2 (normalization defines what is checked). **Owner**: coordinator + one builder.
- **Acceptance examples**:
  - Given a workspace owns `park-therapy`, typing `Park Therapy` shows "taken" and offers `park-therapy-2`; clicking it fills the handle, marks it edited, and re-checks it.
  - If `park-therapy-2` is also taken, the offer is `park-therapy-3`; the suggestion offered is always itself verified free.
  - Answers arriving out of order: the response for `park` arriving after the response for `park-t` never replaces what is shown for `park-t`.
  - The RPC returns only a boolean; a test asserts it exposes no name, id or count, and that `anon` cannot execute it.
  - The RPC is not called for a handle that fails T2's format or length rules.
  - With the RPC erroring, the field says availability could not be checked and Continue is available (OBI-9).
- **Verification**: a psql contract test `supabase/tests/workspace_handle_rpc_contract.sql` plus a `supabase:test:workspace-handle-rpc` script, following the existing contract-test pattern; a `database-contract.test.ts` entry for the generated types; component tests for debounce, staleness and the offline path with a faked action. `pnpm --filter web test`, `typecheck`, `lint`, and the new psql contract script against the local stack.
- **Excludes**: the submit-time collision path (T4); the create-workspace form (T5).

### M3.T4 — Server validation failures reach their field

- **Scenario**: a person who reaches the final screen and still hits a server-side rejection is returned to the step holding the offending field, with the message on that field and every other answer intact (OBI-8).
- **End-to-end boundary**: `OnboardingValidationError` values gain a field mapping → the store distinguishes a handle unique violation (Postgres `23505` on the handle index) from other failures, so `application.complete` can return a specific `workspace_handle_taken` instead of collapsing everything into `onboarding_failed` → the flow routes the error to its step and field rather than rendering one sentence on the Done step → the generic banner remains only for genuinely unattributable failures.
- **Depends on**: T2. **Owner**: coordinator + one builder.
- **Acceptance examples**:
  - A handle taken between the availability answer and submit: the flow lands on the Workspace step with "That handle was just taken" on the handle field; first name, vertical, sensitivity, source and invites are unchanged; submitting again with a free handle succeeds.
  - `first_name_required` returns the person to the Name step with the message on First name.
  - A store failure that is not a unique violation still renders the existing generic banner, and the IMAP `source_error` path with its "Skip source and finish" button is unchanged.
  - A store test proves a unique-violation error is mapped to `workspace_handle_taken` and any other error to `onboarding_failed`.
- **Verification**: `features/onboarding/application.test.ts`, `features/onboarding/supabase-store.test.ts`, `onboarding-flow.test.tsx`; the existing IMAP fallback test must still pass untouched. `pnpm --filter web test`, `typecheck`, `lint`.
- **Excludes**: the create-workspace form (T5).

### M3.T5 — Create-workspace form shares the same behavior

- **Scenario**: a member who joined by invitation creates her own workspace from the switcher and gets the same derived handle, the same field errors, the same live availability check and the same taken-handle message (OBI-10, D4).
- **End-to-end boundary**: `create-workspace-form.tsx` derives its handle from the name through the shared module, uses the same validation and availability hook, and `mapWorkspaceActionError` plus the form surface a taken handle at the field instead of "Could not create workspace."
- **Depends on**: T2, T3, T4. **Owner**: coordinator + one builder.
- **Acceptance examples**:
  - Typing `Bako Studio` fills the handle `bako-studio`; editing the handle stops it following.
  - A taken handle is reported at the field with a working suggestion, before submit.
  - A collision at submit shows "That handle was just taken" at the field and keeps the name and description already typed.
  - The existing behavior of creating a workspace with a free handle, and the redirect to `/home/settings`, is unchanged.
- **Verification**: a component test for the form, `features/workspaces/application.test.ts` for the error mapping, plus the exit-gate step 8 run by hand. `pnpm --filter web test`, `typecheck`, `lint`.
- **Excludes**: workspace settings' handle editing, beyond what the shared rule changes incidentally.
