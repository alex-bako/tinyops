# M4 — Home is the client list

## User outcome and exit gate

Outcome: signing in puts the workspace's real clients on screen. The search bar sits above them and narrows them as you type. Every sidebar row goes somewhere. Nothing on the signed-in surface is a hardcoded example any more.

Exit gate (observable, local stack, driven by hand in a browser after the suite is green):

1. Sign in as a workspace owner with seeded clients. `/home` shows a header naming the workspace and its real client count, the search bar, the status tabs with real counts, and one row per client. The greeting, "Needs attention", "This week", "Recently viewed" and the four "Quick actions" buttons are gone — no "Jamie", no "Wednesday, May 8", nowhere on the page.
2. The sidebar shows Home, Data sources and Settings. No Clients, no Tasks, no "Pinned views" group.
3. Type `mari` in the search bar: the rows narrow to matching clients while you type, the footer count follows, and the dropdown offers to open an exact match. The dropdown does not cover the rows it is narrowing. There is exactly one search input on the page.
4. Press Enter on the dropdown match: the client's profile opens. Its breadcrumb reads `Home > <client name>` and its back link returns to `/home`.
5. Clear the search: all rows return. Type `zzzzz`: the rows area says nothing matches the search and offers to clear it.
6. Open `/home/clients` directly: it lands on `/home`. Open a `/home/clients/<slug>` link directly: the profile loads unchanged.
7. Sign in as a freshly onboarded owner whose workspace has no clients: `/home` says the workspace has no clients yet and offers Import and New client. It does not say "No clients match these filters".
8. With `/home` open, insert a client into the workspace from a second session: the row appears without a manual reload.
9. Seed a workspace at the top of the target range (~2,000 clients): `/home` renders and scrolls without stalling, and typing in the search bar stays responsive.

## Scope and non-goals

In scope: HOME-1 through HOME-12 across `/home`, `/home/clients` and the sidebar.

Non-goals: building a real "Needs attention" summary (the counts it faked have no definition or query yet — deleting the fake is this milestone, computing a real one is a later one); building Tasks or Pinned views; making "View", "Import" and "New client" functional beyond their current behavior; any change to the list's columns, sorting, filters or cohorts; any change to the client profile; server-side pagination of the client list; onboarding, Join, switcher, settings and data-source surfaces.

## Entry dependencies

None. M4 is independent of M1, M2 and M3. It touches `/home`, `/home/clients` and the sidebar; M3 touches onboarding and the create-workspace form. The only shared fact is that both feed a person to `/home`, which is behavior M4 improves and does not move.

## Risks and material decisions

- **Decided (D1)**: full replacement. The example sections are deleted, not stubbed or hidden behind a flag. The consequence to accept openly is that the at-a-glance summary disappears until it can be computed for real; it was never true, so nothing accurate is lost.
- **Decided (D2)**: every dead nav entry goes, not only Clients. Tasks and Pinned views return as one array entry each when those features ship.
- **Decided (D3)**: one search bar, driving the list. This is the only bullet that is real work rather than relocation.
- **Risk**: two nav definitions exist and only one is live. `WORKSPACE_NAV_GROUPS` drives the sidebar; `NAV_GROUPS` in `lib/navigation.ts` is referenced only by its own test, while `APP_ROUTES` in the *same file* is live and drives breadcrumbs. Editing the wrong one produces a green test and an unchanged sidebar, or a changed sidebar with a stale breadcrumb trail. T2 must resolve the duplication, not work around it.
- **Risk**: the search bar currently queries the server per keystroke and caps at 8, while the list holds every row. If T3 leaves both paths live, the dropdown and the rows can disagree about which clients exist — the exact failure the domain invariant forbids. A2 resolves this by deriving both from the loaded rows.
- **Risk**: `_view-model.test.ts:93` asserts against the literal source path `app/(app)/home/clients/_view-model.ts`. Moving files breaks it in a way that reads as an unrelated failure.
- **Risk**: the realtime refresh components are split across surfaces — `WorkspaceClientsRealtimeRefresh` is mounted in the sidebar, `ClientProfileRealtimeRefresh` inside `ClientsPageClient`. Relocating the list can silently drop one and leave HOME-13 untested-but-broken. Verify the refresh by hand (gate 8), not by inspection.
- **Risk (accepted)**: the list is uncapped by design and the whole workspace ships to the browser. Existing row windowing is what makes that acceptable, and gate 9 is what proves it at the top of the stated range. If it fails there, that is a finding for a separate milestone about list scale, not a reason to add pagination inside this one.

## Tracer bullets

### M4.T1 — Home renders the client list

**User scenario**: Ada signs in and sees her 137 clients, with the search bar above them. A freshly onboarded Mia sees "no clients yet" and how to add some.

**End-to-end boundary**: `/home` route → client reader (`listClients`) → the existing toolbar and table components → rendered rows. Includes the `/home/clients` redirect and the back-link and breadcrumb retargeting.

**Dependencies**: none. First slice.

**Acceptance examples**:
- `/home` renders the status tabs with real counts, the cohort select, and one row per client of the active workspace.
- No string from the deleted sections appears anywhere in the rendered page: not "Jamie", "Wednesday, May 8", "Needs attention", "This week", "Recently viewed", or the four quick-action labels.
- The header names the active workspace and a client count equal to the number of rows.
- A workspace with zero clients renders the empty-workspace state with Import and New client, and specifically not `CLIENT_LIST_EMPTY_MESSAGE`.
- `/home/clients` redirects to `/home`; `/home/clients/<slug>` still renders the profile; the profile's back link and breadcrumb point at `/home`.
- Inserting a client from another session adds its row to an open `/home` without a reload.

**Verification**: component tests over the new `/home` for the populated and zero-client cases and the absence of the deleted strings; a route test for the redirect; the existing client-list and table suites kept passing with their paths updated; gates 1, 6, 7 and 8 by hand.

**Excludes**: the sidebar (T2) and any change to search behavior (T3). The toolbar keeps its own filter field for the duration of this slice, so the page ships with two search inputs until T3 — deliberate, and the reason T3 follows immediately.

**First sources**: `app/(app)/home/page.tsx`, `app/(app)/home/_data.ts`, `app/(app)/home/clients/page.tsx`, `_components/clients-page-client.tsx`, `_view-model.ts`, `app/(app)/home/loading.tsx` and `clients/loading.tsx` (reconcile the two skeletons), `app/(app)/home/clients/[slug]/page.tsx` and `not-found.tsx` (back links), `lib/navigation.ts` (`APP_ROUTES`, `deriveAppCrumbs`).

### M4.T2 — Every sidebar row leads somewhere

**User scenario**: Ada's sidebar reads Home, Data sources, Settings. Nothing in it does nothing.

**End-to-end boundary**: the nav definition → `buildSidebarNavGroups` → the rendered sidebar, plus the breadcrumb route table that must stay consistent with it.

**Dependencies**: T1. Removing Clients before Home shows the client list would leave the list reachable only by deep link.

**Acceptance examples**:
- The sidebar renders exactly Home, Data sources and Settings for a real workspace.
- No rendered nav row lacks a destination.
- A client profile's breadcrumb reads `Home > <client name>`, with no dangling "Clients" crumb.
- One nav definition drives the sidebar; the unused duplicate is gone rather than left to drift, and no test asserts against a definition the app does not render.

**Verification**: a sidebar test asserting the exact set of rendered entries and that every one has an `href`; the breadcrumb suite updated for the collapsed trail; `lib/navigation.test.ts` and `features/workspaces/view-models.test.ts` reconciled with whichever definition survives; gates 2 and 4 by hand.

**Excludes**: removing the `tasks`/`march`/`feedback`/`dnc` keys from `WorkspaceSidebarCounts` (A5), and the mock rows in `mock-data.ts` (A4).

**First sources**: `features/workspaces/navigation.ts`, `features/workspaces/view-models.ts` (`COUNT_KEYS`, `withWorkspaceCount`), `lib/navigation.ts`, `components/app-sidebar.tsx`.

### M4.T3 — One search bar, and it drives the list

**User scenario**: Ada types `mari` once, in one box, and gets both: two rows to compare, and the option to jump straight into Mariko's profile.

**End-to-end boundary**: the search input's query → the list's filter state → the rendered rows and footer count; and the same query → the dropdown's jump and action items. Both read the rows already loaded.

**Dependencies**: T1.

**Acceptance examples**:
- Typing in the top bar narrows the rows below and the "n of m shown" count follows.
- The toolbar's own "Filter by name or email" field no longer exists; exactly one search input is rendered.
- The dropdown offers an exact match to open, plus its existing non-client actions, and does not obscure the rows being filtered.
- Search and the status/cohort filters compose: narrowing by text inside the "Active" tab shows only active clients matching the text.
- A search matching nothing shows the no-match state with a way to clear, distinct from the empty-workspace state.
- The dropdown and the rows never disagree about which clients exist, because one set of loaded rows answers both.

**Verification**: component tests typing character by character and asserting rows, footer count and dropdown contents together; a test that search and filters compose; a test distinguishing the two empty states; gates 3 and 5 by hand.

**Excludes**: changing what the filters or cohorts mean; adding sorting; server-side pagination.

**First sources**: `app/(app)/home/_components/home-search.tsx`, `home-search-model.ts`, `app/(app)/home/actions.ts`, `app/(app)/home/clients/_components/clients-toolbar.tsx`, `_view-model.ts` (`useClientListView`, `filters.query`).

## Slice order and dependencies

1. `M4.T1` Home renders the client list — first slice, small and useful on its own.
2. `M4.T2` Every sidebar row leads somewhere.
3. `M4.T3` One search bar, and it drives the list.

Dependencies are acyclic: T1 → none; T2 → T1; T3 → T1. M4 exit needs all three.
